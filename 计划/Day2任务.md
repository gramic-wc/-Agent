## ⚠️ 先读这个：两条环境坑（不先解决，后面一半命令会莫名失败）

这两个坑是写这份文档时实际踩到的，**不是理论问题**。花 5 分钟先搞定。

### 坑 1：命令后面带的 `2>$null` 会把退出码变成 1

你会看到很多命令以 `2>$null` 结尾。它只是用来屏蔽 httpx 的 `INFO` 日志。
但在 PowerShell 里，只要 stderr 有东西被丢弃，`$LASTEXITCODE` 就会变成 1。

**结果**：命令其实**成功**了，输出也对，但退出码是 1。不影响你读结果，只是别被它吓到。

### 坑 2：`python -c "...中文..."` 在 PowerShell 5.1 里会被中文破坏

实测：命令里的中文会因为 PowerShell 的编码问题被搞坏，报错如下：

```
SyntaxError: (unicode error) 'utf-8' codec can't decode byte ...
```

**这不是代码写错了，是 PowerShell 的锅。** 两个解法：

**解法 A（推荐）：中文参数写成 `\u` 转义**

```powershell
uv run python -c "print('\u6392\u6c14\u6e29\u5ea6\u9ad8')"   # 输出：排气温度高
```

> 这就是为什么下面有些命令的 query 里看到 `'\u6392\u6c14'` 这种怪东西——
> 不是乱码，是故意的。运行时它会变回中文。**照抄就行，不用看懂。**

**解法 B：把代码写成 `.py` 文件再跑**

```powershell
notepad tmp_check.py      # 把 python -c 里的代码粘进去，保存
uv run python tmp_check.py
```

## 0.2 搞懂「一次检索」到底发生了 4 件事

❓ **为什么先讲这个**：今天所有的数字（命中率、污染率、块长）都要用这条链路去解释。
如果不先看懂链路，你只会得到一堆数字但不知道它们为什么是这样。

**你敲一句 `search_manual("排气温度高")`，代码里其实发生了 4 步：**

```
你的一句话
"排气温度高"
      │
      ├──① dense（向量检索）────────────────────────────────┐
      │   "排气温度高" ──embedding──> [0.023, -0.51, ...]  │  1024 个数字
      │   拿这 1024 个数字去 Qdrant 里找"坐标最近"的卡片     │  取 30 张
      │   ← 靠"意思像"，能跨过措辞差异                      │
      │                                                     │
      ├──② sparse（BM25 关键词检索）────────────────────────┤
      │   "排气温度高" ──jieba分词──> ["排气","温度","高"]  │
      │   在全文里算每个词出现得多不多、稀有不稀有            │  取 30 张
      │   ← 靠"字一样"，能精准命中 GA55 / E-201 这种代号      │
      │                                                     │
      ├──③ RRF 融合 ────────────────────────────────────────┤
      │   两边的 30 张合并，按"在两个榜上都靠前"重新排         │  留 30 张
      │   ← 只看排名，不看原始分数（两路分数不可比）           │
      │                                                     │
      └──④ rerank 重排 ─────────────────────────────────────┤
          把候选的原文 + 你的问题交给一个专门的"重排模型"      │  取 6 张
          让它逐条打"相关性分"，重新排序                       │
          ← 最贵也最准，所以只在最后 30 条上做                 ┘

最终 6 张卡片（带文档名 + 页码）返回给你
```

**对应的代码，全在 `src/eqagent/retrieve/hybrid.py`：**

| 步骤 | 函数 | 行附近 | 关键常量 |
| --- | --- | --- | --- |
| ① 向量 | `Retriever._dense()` | `_dense` | `DENSE_K = 30` |
| ② 关键词 | `Retriever._sparse()` | `_sparse` | `SPARSE_K = 30` |
| ③ 融合 | `Retriever.search()` 里那段 `for hits in (dense, sparse)` | | `RRF_K = 60` |
| ④ 重排 | `llm.rerank(...)` | `_rerank` / `llm.py` | `RERANK_K = 30` |

💡 **懂了没**：下面这句对不对？
> "纯 BM25 搜不到'跳机怎么办'，是因为手册里可能根本没用'跳机'这两个字。"

✅ 对。BM25 只认**字面相同**的词。'跳机' 在手册里通常写成 "跳闸停机"、"高温停机"、"trip"。
而向量检索（①）不认字，认"意思"，所以能跨过去。
**但向量也有短板**：`E-201` 这种纯代号，向量空间里没什么"意思"可言，反而是 BM25 更准。
→ 这就是为什么必须有两条路。

## 0.3 亲手造一个「检索透视镜」

🎯 **这一步在干嘛**：写一个 10 行的小脚本，把上面 4 步的每一步结果**分别打印出来**。
以后调检索、看排名的变化，全靠这个工具。

❓ **为什么自己做而不是直接跑现成的**：因为 `search_manual()` 只给你"最终 6 条"，
你不知道这 6 条是被哪一路召回的、融合前排第几、重排后升了还是降了。
**看不清中间过程，就永远调不动检索。**

⌨️ **敲什么**：新建文件 `scripts/search_debug.py`，把下面整段复制进去

```python
"""检索透视镜：同一句 query，分别打印 4 步的结果。

为什么需要它：
    search_manual() 只给最终结果。调检索时必须知道
    「这条是被向量找上来的 还是被关键词找上来的 还是被重排救回来的」。

用法：
    uv run python scripts/search_debug.py "排气温度高 处理" --device GA55
    uv run python scripts/search_debug.py "3号车间GA55运行20分钟后排气温度高跳机" --show 3
"""

from __future__ import annotations

import argparse
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parents[1]
sys.path.insert(0, str(ROOT / "src"))

from eqagent.retrieve.hybrid import (  # noqa: E402
    DENSE_K,
    RERANK_K,
    SPARSE_K,
    get_retriever,
)
from eqagent import llm  # noqa: E402


def show(title: str, hits, n: int) -> None:
    print(f"\n{'=' * 78}\n{title}（{len(hits)} 条）\n{'=' * 78}")
    for rank, h in enumerate(hits[:n], 1):
        page = h.payload.get("page", 0)
        model = h.payload.get("device_model", "-")
        btype = h.payload.get("block_type", "-")
        text = (h.text or "").replace("\n", " ")[:56]
        print(f"  {rank:2d}. [{model:9s}] p{page:<4d} {btype:6s} {h.score:8.4f}  {text}")


def main() -> None:
    ap = argparse.ArgumentParser(description="检索透视镜")
    ap.add_argument("query")
    ap.add_argument("--device", default=None, help="只在这些设备里找，如 GA55")
    ap.add_argument("--show", type=int, default=5, help="每题打印前几条")
    args = ap.parse_args()

    r = get_retriever()
    print(f"\nQuery  : {args.query}")
    print(f"Device : {args.device or '不过滤'}")

    dense = r._dense(args.query, DENSE_K, args.device, None)
    sparse = r._sparse(args.query, SPARSE_K, args.device, None)
    show(f"① dense（向量）top{DENSE_K}", dense, args.show)
    show(f"② sparse（BM25）top{SPARSE_K}", sparse, args.show)

    # ③ 只看融合排名，不做重排
    fused: dict[str, float] = {}
    pool: dict[str, object] = {}
    for hits in (dense, sparse):
        for rank, h in enumerate(hits):
            fused[h.chunk_id] = fused.get(h.chunk_id, 0.0) + 1.0 / (60 + rank + 1)
            pool.setdefault(h.chunk_id, h)
    ranked = sorted(fused.items(), key=lambda kv: kv[1], reverse=True)[:RERANK_K]
    cands = []
    for cid, _ in ranked:
        h = pool[cid]
        h.score = fused[cid]
        cands.append(h)
    show(f"③ RRF 融合（无重排）top{len(cands)}", cands, args.show)

    print(f"\n{'=' * 78}\n④ rerank 重排（这一步要联网，约 1~2 秒）\n{'=' * 78}")
    reranked = llm.rerank(args.query, [h.text[:800] for h in cands], top_n=args.show)
    if not reranked:
        print("  rerank 没返回（可能 RERANK_ENABLED=0 或网络失败），退回 RRF 顺序")
        return
    for new_rank, (idx, score) in enumerate(reranked, 1):
        h = cands[idx]
        old = idx + 1
        delta = old - new_rank
        mark = f"↑{delta}" if delta > 0 else (f"↓{-delta}" if delta < 0 else "=")
        page = h.payload.get("page", 0)
        model = h.payload.get("device_model", "-")
        text = (h.text or "").replace("\n", " ")[:50]
        print(f"  {new_rank:2d}. (融合第{old:2d} {mark:3s}) [{model:9s}] p{page:<4d} {score:7.4f}  {text}")
    print("\n↑ 表示重排后升了（重排认为它更相关），↓ 表示降了。")


if __name__ == "__main__":
    main()
```

# 阶段 1 · 固定 query 召回率（50 分钟）

## 1.1 先搞懂"召回率"和"命中"的定义

🎯 **这一步在干嘛**：把"检索准不准"变成一个能跟别人说的数字。

❓ **为什么必须先定义清楚**：如果不定义，"我看了下感觉还行"这种结论没有任何价值，
而且明天调完参数你没法证明"变好了一点"。**定义就是进度条。**

**今天用这三个词：**

| 词 | 定义 | 今天的用法 |
| --- | --- | --- |
| **top_k** | 返回前 k 条 | 用 **5** |
| **命中（hit）** | top_k 里有**该设备**的、**内容相关**的页面 | 人工判定 |
| **召回率 Recall@5** | 命中条数 ÷ 总条数 | 8 条里命中 6 条 = 0.75 |

**"相关"到底怎么判？** 给你一条可操作的判据（**别凭感觉**）：

> 假设我是维修工，只看到这一页，能不能据此开始动手排查/维修？
> - **能**（哪怕只能做第一步）→ 算命中
> - **不能**（看完还是不知道该怎么查）→ 不算命中

再加一条硬条件：
> 页面所属 `device_model` **必须**跟问题里的设备一致（问 GA55 却返回电机内容，一律不算命中）。

## 1.2 跑第一批 query

### 六类失败，逐条翻译成“人话 + 在透视镜里长什么样”

先记住透视镜的 ①~④ 是什么（对应 `scripts/search_debug.py` 的四段输出）：

| 段 | 是什么 | 人话 |
| --- | --- | --- |
| ① dense | 向量检索 top30 | **靠“意思像”**：你说“跳机”，它也能找到“高温停机” |
| ② sparse | BM25 关键词 top30 | **靠“字一样”**：代号 `E-201`、`GA55` 靠它才准 |
| ③ RRF | 两路合并后 top30 | **只看排名不看分数**，两边都靠前的排前面 |
| ④ rerank | 重排后取 top5/6 | 最贵也最准的一步，**但会误判，也会把对的东西压下去** |

| 类型 | 人话（到底是什么坏了） | 透视镜里的信号（看哪一段） | 先试什么 |
| --- | --- | --- | --- |
| **A. 数据缺失** | 手册里根本没有这句话 → 检索再牛也搜不出来 | ① ② 里都没有“该有的那页”；再去 `chunks.jsonl` 全文 grep 也搜不到 | 补手册 / 修解析（不是调检索的事） |
| **B. 分词失效** | 你说的词，手册里没这个字 | ② sparse 结果**很少**或全是噪声（比如只有几条无关页），① 却正常 | 加同义词表 / 加领域词典 |
| **C. 块太碎** | 命中了，但**只剩半句话**（表格被切成单行、步骤被切断） | ① ② 都命中了正确页，但返回的 `text` 开头结尾明显是断的（比如预览只有 `【表格】` 开头、后面表头和数据都没了） | 调 `chunker.py` 的切块逻辑（Day 3） |
| **D. 块太大** | 命中了，但一块 800 字，里面**什么都提一句**，重排打分被拉平 | ① ② 里同一块特别长，④ 的分数都很接近（0.16x 一档，分不开） | 减小 `max_len` / 加子块标题 |
| **E. 重排误判** | ① ② **已经把正确答案捞到了**，④ 又给它压下去了 | ② 或 ③ 里能看到正确页排前几，④ 的 top5 里**没了**或掉到后面 | 调 `RERANK_K` / 换重排模型 / 给它喂标题上下文 |
| **F. 跨设备污染** | 命中的内容和问题无关，因为它是**另一台设备的**手册页 | ④ 结果的 `device_model` 跟你问的对不上（问 GA55 出现 VMC850） | 设备过滤（阶段 3 重点） |
| **G. 索引与切块不同代**（Day3 新增） | 库里文本和你屏幕上看到的**不是同一版**：改完 `parse.py` 只重切了 jsonl、没重建向量库 | 同页同类型的预览文字像“隔壁块”；① dense 条数明显少于请求数（本次 20/30）；点数 ≠ jsonl 行数 | 重建向量库 + 自检“点数==行数、孤儿点 0、不一致率<1%” |
| **H. 名额截断**（Day3 复核新增） | ③ ④ 里都在、也没掉位，就是**过了 `top_k`（默认 6）那一刀** | ②或③排前几，④ 也还在 30 条里，**但名次 > 6**（本次：②#3 → ③#7 → ④#7） | 调 `top_k`（6→10），或把 rerank 输出与 top_k 解耦；**不是**调 `RERANK_K` |

#### 三类最容易搞混的，再多说两句

**E（重排误判）为什么最坑？** 因为它会让你的“调参”走错方向。你看到 top5 不对，第一反应是去调向量模型或切块，但其实**前两步是对的、被最后一步毁了**。判据只有一条：**去 ② 和 ③ 里找那个正确页，看它在不在、排第几**。在里面 → 是 E；不在里面 → 才是 A/B/C/D。

> ⚠️ **今天踩过的坑（必读）**：判 E **不能只看 `--show 5` 的 ④**。示范 1 那条，④ 的完整 30 条里表 20 排**第 7** —— 它**没被重排压下去**，只是被 `top_k=6` 截断（那是 **H**）。
> 所以 E 的完整判据是两句话：**① 在 ②/③ 里靠前；② 在 ④ 的完整名单里真的掉到后面或消失**。少一句就会把 H 冤枉成 E，然后去调 `RERANK_K`（白干）。

**C（块太碎）怎么一眼认出来？** 看 `text` 预览的**开头和结尾**。表格块经常是 `【表格】| 单位名称：| | |` 这种——**表头全在、数据没了**，那就是切碎了。（你手上 `GA55_维护保养规范 p13 / p20` 这两页反复出现在各种 query 里，性质就是“整页保养记录表”，很可能同时踩 C 和 D。）

**F（跨设备污染）为什么不算“检索不准”？** 因为它在语义上**没错**——空压机的“油压不足”和加工中心的“油压不足”确实是同一个意思。错的是**没告诉系统这是哪台设备**。所以解法不是改模型，是**加过滤条件**（阶段 3）。

### 判决流程（照着走，不要凭感觉）

```
拿一条不理想的 query
   │
   ① 先去 chunks.jsonl 全文 grep 关键词 ──搜不到──> A 数据缺失（到此为止）
   │ 搜到了 ↓
   ② 看 ④ 的 top5 里 device_model 对不对 ──有别人的设备──> F 跨设备污染
   │ 都对 ↓
   ③ 去 ② sparse 和 ③ RRF 里找那个“正确页”
   │        ├─ 在，而且排很靠前，但 ④ 没了/掉了 ──> E 重排误判
   │        ├─ ② sparse 里几乎没有它（① 有） ────> B 分词失效
   │        ├─ 在，但 text 预览是断的 ───────────> C 块太碎
   │        └─ 在，但 text 是一大段、④ 分数都挨在一起 ─> D 块太大
   └─ 以上都不是 ──> 重新确认“正确页”到底是哪页（可能你自己判错了）
```

> ⚠️ **顺序不能反**：**先证明数据在不在（A），再怪检索。** 90% 的“检索不行”最后发现是“库里没有/切碎了”。

#### 判决流程怎么真的做：抄一张“物流单”

上面那张流程图是**逻辑**，真正动手时你只需要干一件事：**盯住“正确页”这一个坐标，看它在 ① ② ③ ④ 四站各排第几。**
跟查快递一样：包裹没到手，就看它是哪个中转站丢的。

**第 0 步 · 先把“坐标”定下来**（全程唯一需要你判断的地方）

坐标 = **文档 + 页码 + 块类型**，三个都要。因为同一页经常被切成好几块：`p21 text`（讲绝缘电阻）和 `p21 table`（表20 振动强度限值）是**两个不同的东西**，混了就会判错类型。

| 怎么定坐标 | 怎么做 |
| --- | --- |
| 从期望原因反推 | 读 `data/dev_cn.json` 的 `expect_causes`（如“冷却器,风扇,油位”），去手册里找讲这个原因的页 |
| 直接 grep 原文（最稳） | 在 `chunks.jsonl` 里搜关键词，把 `device_model / page / block_type` 三个字段抄下来 |

```powershell

```

| 站 | 正确页在不在 | 第几名 |
| --- | --- | --- |
| ① dense（向量） | | |
| ② sparse（BM25） | | |
| ③ RRF（融合） | | |

两个采集技巧（不这么做基本判不出来）：

1. **`--show 30`，别看 top5**。正确页常常在 ② 排第 3、在 ④ 的 top5 之外 —— 只看 5 条，你等于没证据。
2. **④ 每行括号里已经写着它在 ③ 的名次**：`(融合第 2 ↓3)` = 在 ③ 排第 2，被重排压到第 5。所以 **E 类判定最快**：括号里数字掉得多，就是被重排坑的。

**第 2 步 · 看它死在哪一站 → 直接就是类型**

| 正确页的情况 | 判定 |

# 阶段 3 · 跨设备污染（30 分钟）

## 3.1 先看现象

🎯 **这一步在干嘛**：量化"问 A 设备却返回 B 设备内容"有多严重。

❓ **为什么这很严重**：给空压机的问题返回加工中心的步骤，**不是"相关性差"，是"会害人"**。
工人照着加工中心的刀库步骤去修空压机，后果比不回答更糟。

⌨️ **敲什么**

```powershell
uv run python -c "from eqagent.agent.tools import search_manual; qs=['\u6392\u6c14\u6e29\u5ea6\u9ad8','\u4e3b\u8f74\u5f02\u54cd','\u8f74\u627f\u6e29\u5ea6\u9ad8','\u4f3a\u670d\u62a5\u8b66','\u5200\u5e93\u5361\u5200','\u632f\u52a8\u8d85\u6807']; [print('\n###',q,'\n  不过滤:',[h['device_model'] for h in search_manual(q,top_k=5)],'\n  GA55  :',[h['device_model'] for h in search_manual(q,device_model='GA55',top_k=5)]) for q in qs]" 2>$null
```

👀 **你应该看到什么**：6 个块，每块两行设备列表。

📌 **真实运行结果（2026-11-20）**：

```

主轴异响    不过滤: ['YE3-160M','VMC850','VMC850','YE3-160M','YE3-160M']  ← ❗ 混了 2 种设备

振动超标    不过滤: ['YE3-160M','YE3-160M','YE3-160M','GA55','GA55']   ← ❗ 3 条后污染
```

**污染率 = 3 / 30 = 10%**

💡 **这是一个重要发现，而且它和我们原先的预期不一样**：

之前（Day 1）看到 `伺服过载 排查` 第 2 名是 GA55，以为污染很严重。
但用**短 query** 测，污染只有 10% —— 说明**长 query 比短 query 更容易污染**（信息多 → 向量匹配更易乱拉）。
**这是很有价值的观察，记进 metrics.md。**

🔍 **更值得注意的是一个更隐蔽的问题**：

`轴承温度高 不过滤` 返回的全是 `YE3-160M`，看起来”对了“，但仔细想：
> “温度高”这三个字，**三台设备都有**。
> 返回全是一种设备，不是因为”认对了“，而是因为**它们的向量正好更近**。
> —— 一旦换了措辞，结果就可能变成另一台设备的。**这种”看起来对“最危险。**

> 📌 **再看一个结论**：加了 `device_model='GA55'` 后，**所有 6 条都返回纯 GA55**。
> 说明**过滤在技术上完全生效**。真正难的是**“型号从哪来”**（见 3.3）。

## 3.3 想清楚"过滤放哪一层"

这是今天唯一需要动脑子的设计题，**想清楚了，Day 9 就是照着做**。

**三个位置可以放过滤：**

| 位置 | 怎么做 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 检索前** | `build_filter(device_model=...)` 传给 Qdrant | 最省，库里就不返回错的 | 型号必须**先认对**，认错就全错 |
| **B. 检索后** | 拿到结果再筛掉不匹配的 | 简单 | 已经浪费了 top_k 名额（5 条里 3 条被筛掉，等于只剩 2 条有用） |
| **C. 重排前** | 融合完 30 条再筛 | 平衡 | 实现稍微复杂一点 |

**现在的代码是 A**（`hybrid.py` 的 `_dense` / `_sparse` 都接了 `device_model`）。

**但这里有个真问题**（今天就记下来，Day 8 会撞上）：

> **型号从哪来？**
> - 用户直接说"GA55" → 容易，正则匹配 `GA55|VMC850|YE3` 就行
> - 用户说"3号车间的空压机" → 得从 `config.py` 的 `ALIASES` 里认（"空压机" → GA55）
> - 用户说"那台响的机器" → **认不出来**
>
> 认不出型号时怎么办？两个选择：
> 1. 不过滤，靠内容自己竞争（有污染风险）
> 2. 直接转人工（安全但体验差）
>
> **这道选择题，Day 8 的 `identify` 节点必须回答。** 今天先记着。

💡 **懂了没**：如果"型号识别"错了（把空压机认成加工中心），加过滤后结果会怎样？
→ **比不过滤还糟**。不过滤至少有可能靠内容混进来，过滤了就是 100% 返回错的设备。
**所以"过滤"和"认型号"必须一起考虑，不能只做一半。**

```
我看懂了 RRF 的公式是：score = ______________________

```

**参考**：`score(chunk) = Σ over 每一路 1/(60 + 该路排名)`。
意思是"在所有召回到它的路里，排名越靠前，加分越多；两路都靠前，分最高"。
**60 是个经验常数**，作用是让排名第 1 和第 100 的差距不至于过大（平滑）。
